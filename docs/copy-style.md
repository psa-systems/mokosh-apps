# Copy style

PMS-1335 writes this down so new customer-facing copy does not regress.
Read it before authoring a banner, a confirm dialog, an inline notice, an
email subject, or a help string. These rules apply across the SPA
(mokosh-apps) and anything mokosh-server emits that reaches a customer
(invoice PDF text, email bodies, portal strings).

## The MSP's voice, one statement per line

Customer-facing copy is the MSP speaking, not the system describing
itself in the third person. The reader is a human; the string is what the
MSP would say in person. Prefer:

> We voided this invoice; it stays on record.

Not:

> This invoice was voided by the system. It stays on record as it was and
> cannot be reinstated; raise a new invoice instead.

The second form is a statement followed by an explanatory assertion that
restates it. The first form is what the MSP would say.

## Keep each statement whole

A statement that stops mid-clause reads as a bug. If the message does not
fit the available space, shorten the message, do not truncate it. The
2026-08-21 regression where a 409 handler returned "This form has been
retired and is no longer accepting submissions. An active form" is the
worked example of what this rule prevents (PMS-838).

## Delete sentences the user does not need

If the sentence restates what the badge or the surrounding affordance
already tells the reader, delete it. A "Voided" badge paired with the
sentence "This invoice was voided" leaves one of the two to do the work.
Prefer the badge.

## Totals summarise the money, not every column

An invoice's totals surface shows subtotal, tax, total, credit, and
remaining balance. Discount, line adjustments and intermediate values
belong on the line, not the summary. Save a line for a number the reader
cares about on its own.

## Long explanations become a question-mark link

When a case genuinely needs more than one short sentence, link the
explanation rather than inlining it. The link target lives in the
knowledge base; a surface that would otherwise carry a paragraph gets a
`?` icon + a one-line summary + an anchor the KB article defines.

Pending the KB landing (PMS-800, PMS-1049), the first pass of this rule
is to SHORTEN the inline text and skip the link; add the link once an
article exists at the target.

## ASCII only

No em-dashes, en-dashes, or decorative quotes.

- em-dash (U+2014) becomes a hyphen or a colon.  <!-- em-dash-guard-allow -->
- en-dash (U+2013) becomes a hyphen.  <!-- em-dash-guard-allow -->
- Curly quotes become straight quotes.

The one Unicode punctuation character this rule DOES allow is the
horizontal ellipsis (U+2026, "Loading..."), per the MAPPS-410
convention and the `check-ellipsis-glyph` guard.

A grep over the SPA should return no em-dash or en-dash. The
`check-em-dash` guard runs this automatically on every `just check`
and in CI; the two definitional lines above carry an opt-out marker so
they can spell the characters they describe. This rule also exists in
the global user instructions; this file is the SPA-local statement.

## Where this applies

Customer-facing strings include:

- Banners, toasts, confirm dialogs, inline notices in the SPA.
- Help strings beside inputs.
- Column labels on tables that end up printed or exported.
- Invoice, credit note, quote, request-form and portal text in
  mokosh-apps.
- Email subject lines, body text, and SMS text generated by
  mokosh-server when a human reads them.

Internal pages (`/admin/*`, developer tooling, parity reports) are
excepted. Comments inside code are their own thing, covered by the
global rule in `~/.claude/CLAUDE.md`.

## Not in scope here

- i18n. Mokosh is English-only today; when a second locale lands, the
  copy still has to meet these rules first, and translators work from
  these as the source.
- Marketing copy, which sits outside the application.
